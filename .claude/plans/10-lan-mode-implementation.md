## 2. Ordered implementation tasks

Numbered in dependency order; parallelizable tasks are grouped and marked.

### Phase A — transport-agnostic scaffolding (no NGO API calls yet, pure [File])

1. **`LobbyState`** (`Networking/Session/LobbyState.cs`) — plain C# data shape first (players list: id/name/team/sailorId/ready; mode: Coop/Pvp using the existing `SessionMode` enum from `ISessionProvider.cs`). Write it as a plain serializable class before wrapping it in NGO's `NetworkList`/`NetworkVariable` machinery — gets the shape right and reviewable without Unity open, matching `03` §3 item 7 ("keep lobby state a plain serializable model"). **[File]**
2. **`SessionAdvertisement`** (`Networking/Discovery/SessionAdvertisement.cs`) — serializable struct matching `02` §2's datagram shape (`gameId, protocolVersion, hostName, ip, port, mode, playersCurrent, playersMax, lobbyState`), using `[Serializable]` + `JsonUtility` (already the project's JSON convention per `SaveService.cs`) rather than a new dependency. **[File]**
3. **`LanSessionLauncher`** (`Networking/Session/LanSessionLauncher.cs`) — builds a `Session` (existing `Assets/Scripts/Core/Session.cs` type) from a `LobbyState` snapshot, exactly mirroring what `SinglePlayerLauncher` will do once it exists (napkin item 5) for a single human. **Blocked on nothing structurally**, but for the AI-backfill path specifically, stub it against an `IInputDriver`-typed placeholder (`DummyAIInputDriver` is fine short-term) until real `AIInputDriver` lands (Phase C note below) — don't block LAN scaffolding on Single Player's AI work finishing first. **[File]**

### Phase B — UDP discovery + `ISessionProvider` implementation (parallel with Phase A once #2 is done)

4. **`LanSessionAdvertiser`** (`Networking/Discovery/LanSessionAdvertiser.cs`) — host-side UDP broadcast sender, 1s interval, to `255.255.255.255:47777` per `02` §2. Pure `System.Net.Sockets.UdpClient` usage — no NGO dependency, no MonoBehaviour requirement for the core logic (a thin `MonoBehaviour` wrapper for `Update()`-driven ticking is the only Unity-coupled part). **[File]** for the socket logic; the `Update()`-ticking wrapper is trivially file-writeable too since it doesn't touch scene state.
5. **`LanSessionScanner`** (`Networking/Discovery/LanSessionScanner.cs`) — client-side UDP listener, aggregates advertisements with 3s expiry. Same file/Unity split as #4. **[File]**
6. **`LanSessionProvider`** (`Networking/Session/LanSessionProvider.cs`) — implements `ISessionProvider` (already defined in `Core/ISessionProvider.cs`) by composing #4/#5: `Create()` starts advertising and returns a `SessionInfo`; `StartBrowsing()`/`StopBrowsing()` toggle the scanner and re-surface its results through `SessionDiscovered`/`SessionLost`; `Join()` validates `protocolVersion` (bump-able constant per `02` §2) and hands off to `NetworkBootstrap`'s direct-connect path (#8). Multicast lock acquisition (Android `WifiManager.MulticastLock`, `AndroidJavaObject` interop, only while the scanner is active) lives here or in a small platform-conditional helper it calls. **[File]** for everything except the actual Android multicast-lock JNI call, which is safe to write blind (well-documented Android API) but only *verifiable* on-device — tag that specific method's correctness as needing on-device confirmation, not the whole class.
7. **"Join by IP" fallback path** — `LanSessionProvider.Join(sessionId, connectionData)` already accepts a raw `"ip:port"` string per `ISessionProvider`'s doc comment ("a future online provider fills it with a Relay join code — callers never parse it, only pass it back to Join"); the manual-entry UI just calls `Join` with a hand-typed `connectionData` string, skipping discovery entirely. No new interface surface needed — confirms the existing `ISessionProvider` shape already accommodates `02` §2's "always visible Join by IP" requirement. **[File]** (the call-through logic) + **[Editor/Asset]** (the actual text-entry dialog, tracked under item 7 in the napkin).

### Phase C — NGO wiring (depends on A+B; this is where NGO API surface actually appears)

8. **`NetworkBootstrap`** (`Networking/NetworkBootstrap.cs`) — configures `NetworkManager`+UTP for direct IP:port connect (default port 7777 per `02` §1), wrapped in the `direct(ip,port)`/`relay(allocation)` factory `03` §3 item 3 asks for (write the factory interface now even though only `direct` has an implementation — cheap now, per `03`'s own framing). Host/join entry points call into this. **[File]** for the factory/config logic; **[Editor/Asset]** for the one-time step of placing a `NetworkManager` component in the `MainMenu`/`Match` scenes (NGO requires a scene-resident `NetworkManager` singleton — this is the one piece of this phase that can't be pure script).
9. **`NetworkInputDriver`** (`Networking/Runtime/NetworkInputDriver.cs`) implementing `IInputDriver` (`Core/IInputDriver.cs`) — client side: wraps the client's real driver (`TouchInputDriver`/`KeyboardMouseInputDriver`), samples it locally each tick, and forwards the `InputCommand` to the host via an unreliable-sequenced `ServerRpc`. Host side: for each remote participant, exposes the most-recently-received command from `Sample(time)` — meaning `NetworkInputDriver` needs a host-side variant/mode that *doesn't* wrap a local driver but instead serves buffered network input. Structurally this is two small classes or one class with a host/client mode flag; either is fine as long as `SailorPawn.Initialize` (which already just takes any `IInputDriver`, per `Assets/Scripts/Characters/SailorPawn.cs`) never needs to know which. **[File]** — this is pure C#/NGO RPC code, no scene dependency, matches napkin item 6's tagging exactly.
10. **`NetworkSailorState`** (`Networking/Runtime/NetworkSailorState.cs`) — a `NetworkBehaviour` with `NetworkVariable<float> HP`, `NetworkVariable<int> Ammo`, `NetworkVariable<float> SuperCharge01`, `NetworkVariable<bool> IsKnockedOut`, host-authoritative writes mirroring `SailorPawn`'s existing public getters (`CurrentHP`, `CurrentAmmo`, `SuperCharge01`, `IsKnockedOut` — all already present, this component just needs to read them and push to NetworkVariables on the host, and apply them to presentation on clients). **[File]** for the component logic; **[Editor/Asset]** to actually attach it (+ `NetworkObject`/`NetworkTransform`) to the eventual Sailor prefab (which doesn't exist yet either — see `09` §1a — so this attach step is naturally sequenced after Sailor prefabs land, not before).
11. **`NetworkMatchState`** (`Networking/Runtime/NetworkMatchState.cs`) — NetworkVariables mirroring `MatchController.State`/`CurrentRound`/`CurrentCombatPhase`/round wins, populated host-side from `MatchController`'s existing public events (`OnRoundCountdownStart`, `OnCombatStart`, `OnSuddenDeathStart`, `OnRoundEnd`, `OnMatchEnd` — all already exist, this is pure event-subscription glue, no `MatchController` changes needed). **[File]**
12. **Ability-event ClientRpc relay** — per `02` §1, ability activations broadcast as ClientRpc events (ability id, aim, origin, tick) so clients play the full local VFX instead of syncing every projectile transform. This hooks onto `IAbilityBehavior.Execute(SailorPawn owner)` (`Characters/IAbilityBehavior.cs`) — the *host* still calls `Execute` normally (authoritative hit results per `CombatResolver.ApplyDamage`), but a thin wrapper also fires the RPC so clients spawn the matching visual. **[File]** for the relay/wrapper logic; needs the ability prefabs (projectile visuals etc.) to exist as actual assets to spawn client-side, which ties back to `09`'s art timeline — sequence the *code* now, the *wiring to real VFX prefabs* after `09`'s projectile/ability art lands.
13. **Pawn interpolation/prediction** — client-side presentation smoothing only, per `02` §1 ("keep prediction minimal in v1... do not build rollback"): interpolation on remote pawns via `NetworkTransform`'s built-in smoothing (no custom code needed for LAN's low latency — this is a config/tuning task, not new logic), local prediction + snap-with-lerp reconciliation only for the client's own pawn. **[File]** for the reconciliation logic; **[Editor/Asset]** for `NetworkTransform` component tuning on the prefab.

### Phase D — lobby & session flow (depends on A/B/C's `LanSessionProvider`+`LobbyState`)

14. **Connection approval callback** — validates `protocolVersion`, `rejoinToken` (if reconnecting), lobby capacity, lobby state (reject post-start joins unless rejoining) per `02` §4. Wires into NGO's `ConnectionApprovalCallback`. **[File]**
15. **`rejoinToken` flow** — GUID issued at lobby join (client-cached), 60s reservation window on disconnect, host swaps `AIInputDriver` back out on successful rejoin (again depends on a real `AIInputDriver` existing — see Phase E). **[File]** for the token/timer bookkeeping; the actual driver swap depends on Phase E landing.
16. **Host-loss / backgrounding handling** — transport disconnect detection → "Host left — match ended" state, 10s backgrounding grace before treating an OS-backgrounded client as disconnected, per `02` §4. **[File]**

### Phase E — cross-dependency with Single Player mode (parallel track, not blocking A–D)

17. **`AIInputDriver`** (belongs to `Assets/Scripts/AI/`, not `Networking/`, but LAN co-op and disconnect-takeover both need it) — turns `UtilityStateScorer`'s output + `AIBehaviorProfile`/`AIDifficulty` (all already implemented) into actual `InputCommand`s, replacing `DummyAIInputDriver`. This is napkin backlog item 5's core remaining piece. **Not LAN-specific work, but LAN's exit criteria depend on it** — track it as a shared dependency, don't duplicate an AI driver inside `Networking/`.
18. **`AITeamBuilder`** — same file, same dependency note; LAN's co-op mode (`02` §3: "AI fills Team A remainder and all of Team B") needs this to pick which Sailor each AI-filled slot plays from the 2-Sailor pool.

## 3. Remote (headless) vs Editor-only testing — an important nuance beyond simple [File] tagging

Writing NGO C# classes is [File] work per the convention, but *running* them (even to smoke-test two hosts talking to each other) needs a `NetworkManager` in a scene, which is [Editor/Asset] to set up **once**. After that one-time setup, actual two-instance connection testing *can* run headlessly:
- Unity supports command-line `-batchmode -nographics` launches of a built player; two headless Android/Standalone builds (or a Standalone dev build for fast iteration, since NGO/UTP work identically off-Android for LAN logic — only touch input and the Android multicast lock are platform-specific) can connect to each other over `127.0.0.1` with different ports for a same-machine smoke test, without opening the Editor GUI or touching a physical device.
- This is exactly the kind of loop `11-alpha-build-automation.md` should script: build once, launch two instances with different command-line args (host vs. client, or two clients + a host), watch logcat/stdout for connection success, without a human clicking through the Editor. See `11` §2 for the concrete script.
- **What still needs a human + device**: touch-control verification, real Wi-Fi (not loopback) discovery/multicast-lock behavior, and the two-device soak testing `02`'s M3 milestone calls for (adversarial router setups for Join-by-IP). Don't claim those are automatable — they aren't.

## 4. Milestones (restated from `02` §6, sequenced against the tasks above)

**M1 — Wire-up spike** (Phase A + B + C tasks 8–9 minimum): NGO host + 1 client, direct IP connect, both on Ace pawns (once Sailor prefabs exist — can substitute the current capsule-primitive pawn for an earlier code-only smoke test), movement + basic attack replicated, host-authoritative damage/KO. Exit: playable 1v1 over Wi-Fi, no visible rubber-banding at LAN latency.

**M2 — Discovery + lobby** (Phase B full + Phase D): UDP advertise/scan through `LanSessionProvider`, session list UI, Join-by-IP, multicast lock, protocol versioning, full lobby (co-op/PvP config, team assignment, Sailor picks, ready/start), AI backfill on host (**needs Phase E**). Full Sink or Swim match flow replicated — this is "free" once Phase C tasks 10–11 correctly mirror `MatchController`'s already-complete state machine, no new match-flow logic needed on the network side.

**M3 — Robustness** (Phase D tasks 15–16): disconnect → AI takeover, rejoin window, host-loss handling, backgrounding grace, late-join rejection, version-mismatch UX, two-device soak testing (human-required, see §3).

**M4 — Polish**: lobby QoL, reconnect UX, bandwidth audit (target well under 30KB/s/client per `02` §6 — trivial at this scale but worth actually measuring once traffic exists), CPU cost on the weakest supported device (S21 FE baseline per napkin), co-op difficulty tuning.
